# Тема встречи (topic) для бронирования

Спецификация для issue #13.

## Формулировка проблемы

Гость при бронировании не может сообщить, о чём хочет поговорить на встрече. Владелец видит в списке предстоящих встреч только тип события, имя и email гостя — и не знает тему предстоящей беседы. Теряется контекст, который гость мог бы передать заранее, и владельцу сложнее подготовиться к встрече.

## Решение

У бронирования появляется опциональное поле «тема» (topic) — краткое описание беседы до 300 символов, которое гость указывает в форме бронирования. Тема сохраняется в Booking и отображается владельцу в списке предстоящих встреч. Бронирование без темы работает как раньше: поле необязательное, блок темы в карточке встречи не показывается.

## Пользовательские сценарии

1. Как **гость**, я хочу указать краткую тему беседы при бронировании, чтобы владелец знал, о чём я хочу поговорить.
2. Как **гость**, я хочу оставить тему пустой, чтобы не описывать встречу, когда тема не нужна.
3. Как **гость**, я хочу, чтобы ввод темы ограничивался 300 символами, чтобы не писать текст, который всё равно будет отклонён.
4. Как **гость**, я хочу видеть тему в подтверждении бронирования, чтобы убедиться, что она сохранилась.
5. Как **владелец календаря**, я хочу видеть тему каждой встречи в списке предстоящих встреч, чтобы подготовиться к беседе заранее.
6. Как **владелец календаря**, я хочу, чтобы встречи без темы отображались без блока темы, чтобы карточки оставались аккуратными и без пустых мест.
7. Как **владелец календаря**, я хочу, чтобы пустая строка в теме трактовалась как отсутствие темы, чтобы не видеть пустые темы в списке.
8. Как **владелец календаря**, я хочу, чтобы тема длиннее 300 символов отклонялась бэкендом с понятной ошибкой, чтобы данные оставались консистентными.

## Решения по реализации

### Предметная модель

- **Topic** — новое опциональное поле Booking: краткая тема беседы конкретной встречи (не путать с name/description у EventType, которые описывают шаблон события). Термин вносится в GLOSSARY.md (Booking: «тема»).
- **Точка ввода**: тему вводит гость в форме бронирования. Редактирование бронирований в продукте отсутствует, поэтому другой точки ввода нет (решение принято при триаже #13, можно переопределить отдельной задачей).

### Модель данных

- Колонка `topic VARCHAR(300)`, nullable, в таблице `booking`.
- Обратная совместимость: существующие брони без темы читаются как отсутствие темы.

### Валидация

- Длина ≤ 300 символов через bean validation на входном DTO (в стиле существующих `@NotBlank`/`@Email`), ошибка 400 VALIDATION_ERROR через существующий обработчик в контроллере.
- Пустая/blank строка нормализуется в отсутствие темы (null) при создании брони в сервисе.

### Контракт TypeSpec

- Модель Booking получает опциональное поле topic; модель BookingRequest — опциональное поле topic.
- Меняется только исходный `main.tsp`; сгенерированные артефакты перегенерируются командами из `typespec/package.json`. CI проверяет, что `git diff typespec/generated/` пуст.
- Версии в `typespec/package.json` pinned, lockfile canonical — использовать `npm ci` или `npm install --package-lock-only`. Generated-файлы руками не править.

### Сервис

- BookingService пробрасывает тему из запроса в сохраняемую сущность; остальная логика создания (окно, рабочие часы, оверлапы, блокировки) не меняется.

### Фронтенд

- **Форма бронирования**: необязательный однострочный ввод с ограничением 300 символов (maxLength), значение попадает в payload создания брони; пустое значение не отправляется. Тема показывается в подтверждении создания брони, если задана.
- **Список предстоящих встреч**: тема отображается в карточке встречи, когда задана; блок темы скрывается, когда её нет (по аналогии с существующим поведением guestEmail).

## Решения по тестированию

Хороший тест проверяет внешнее поведение (HTTP-запрос/ответ, отрисованную страницу), а не детали реализации. Используются только существующие швы, новые не вводятся:

- **Контроллер** (BookingControllerTest — MockMvc, фиксированный Clock, Transactional): создание брони с темой ≤ 300 → 201 и тема в ответе; тема 301 символ → 400; без темы и с пустой строкой → 201 (обратная совместимость); `GET /api/bookings/upcoming` возвращает тему.
- **Сервис** (BookingServiceTest — чистые unit-тесты с моками, builder `testEntity()`): blank-тема нормализуется в null; тема пробрасывается в сохраняемую сущность. Приор-арт: существующие тесты create/getUpcoming.
- **Компоненты фронтенда** (vitest + Testing Library, `globalThis.mockFetch`): AdminMeetingsPage — тема видна, когда задана, и скрыта, когда нет; BookingPage — ввод темы, ограничение 300 символов, тема в payload createBooking. Приор-арт: существующие тесты этих страниц.
- Тип `Booking` в моках фронтенда дополняется опциональным topic (генерируется из контракта).

## Вне объема (Out of Scope)

- Редактирование или удаление уже созданных бронирований.
- Тема/заметки у типа события (EventType).
- Многострочный текст, markdown, лимиты больше 300 символов.
- Поиск, фильтрация и сортировка встреч по теме.
- Уведомления/письма с темой встречи.
- Поле темы, редактируемое владельцем (отдельная задача при необходимости).
